# GitHub 日榜推荐短视频自动化流水线 PRD

## 1. 文档信息

- 产品名称：GitHub 日榜推荐短视频自动化流水线
- 文档类型：产品需求文档 PRD
- 版本：v1.0 MVP
- 目标用户：科技自媒体运营者、开发者社区运营者、开源项目推荐账号、AI/开发工具类内容团队
- 首版目标：每日自动发现 GitHub 热门项目，自动生成一条代码 PPT 风格竖屏短视频，并支持人工审核后发布到国内平台

## 2. 背景与问题

GitHub Trending、AI 工具发布、开源项目更新等信息具有明显的时效价值，但传统短视频制作链路依赖人工检索、筛选、写稿、配音、剪辑、封面制作、平台发布和数据记录，导致产能低、响应慢、质量不稳定。

本产品希望把 GitHub 日榜推荐内容生产流程抽象为一条可重复执行的自动化流水线。首版不追求完全无人值守发布，而是优先完成“自动生产 + 人工把关”的 MVP 闭环，降低账号风控、内容事实错误和平台发布不确定性。

## 3. 产品目标

### 3.1 核心目标

- 每日自动采集 GitHub Trending 或等价热度来源中的候选项目。
- 自动补全项目元数据，包括 Star、语言、README、Topics、更新时间、仓库链接等。
- 自动筛选 3-5 个候选项目，并推荐最适合生成短视频的项目。
- 自动生成短视频脚本、标题、简介、标签、封面文案和 CTA。
- 自动生成配音音频、字幕时间戳和竖屏 MP4 成片。
- 支持人工审核脚本、标题、封面和视频成片。
- 支持人工确认后进行半自动发布，并记录发布台账。

### 3.2 成功指标

- 每日可稳定生成不少于 3 个候选项目。
- 人工选择任意候选项目后，可在 10 分钟内产出一条 60-90 秒竖屏 MP4。
- 成片包含配音、动态字幕、项目基础信息、核心卖点、GitHub 链接提示和结尾 CTA。
- 字幕与语音整体同步误差控制在可接受范围内，首版目标为 300ms 以内。
- 每条视频都能生成对应的标题、简介、标签和发布记录。
- 首版发布前必须经过人工确认，避免错误内容直接对外发布。

## 4. 用户与使用场景

### 4.1 主要用户

- 科技自媒体运营者：希望每天稳定发布 GitHub 热门项目推荐视频。
- 开发者社区运营者：希望用短视频形式推广开源工具、AI 工具和技术趋势。
- 内容团队剪辑人员：希望减少重复性找选题、写稿、配音和剪辑工作。
- 账号负责人：希望保留最终审核权，避免自动发布导致账号风险。

### 4.2 典型流程

1. 系统每天定时拉取 GitHub Trending 榜单。
2. 系统补全项目信息并计算推荐分。
3. 系统向运营者推送候选项目列表。
4. 运营者选择一个项目或接受系统默认推荐。
5. 系统生成脚本、标题、标签、配音、字幕和视频。
6. 运营者查看预览并确认是否发布。
7. 系统保存成片、素材和文案，并记录台账。
8. 运营者将素材发布到抖音、视频号、B站、小红书等平台。

## 5. MVP 范围

### 5.1 首版必须支持

- GitHub 日榜候选项目采集。
- GitHub API 元数据补全。
- 候选项目评分与去重。
- LLM 自动生成短视频脚本。
- TTS 自动生成配音音频。
- 字幕时间戳解析和动态字幕渲染。
- Revideo + FFmpeg 生成 9:16 竖屏 MP4。
- 人工审核页面或审核通知。
- 发布素材包导出。
- 发布记录台账。

### 5.2 首版不做

- 不做完全无人值守发布到国内平台。
- 不做数字人口播、口型驱动和虚拟主播。
- 不做多账号矩阵风控系统。
- 不做复杂的 A/B 测试平台。
- 不做全网 AI 新闻爬虫聚合。
- 不做私有大模型训练或 TTS 模型训练。
- 不做自动绕过平台验证码、登录风控或审核机制。

## 6. 总体架构

首版采用“控制面 + 执行面”的架构。

- 控制面：n8n 负责任务触发、流程编排、状态流转、人工确认、失败通知和台账记录。
- 执行面：独立微服务负责采集、评分、LLM、TTS、渲染和资产管理。
- 存储层：对象存储保存音频、字幕、封面、MP4 和中间产物；数据库或表格保存项目、任务和发布记录。
- 人工审核层：通过 n8n 表单、企业微信、Telegram、飞书或简易 Web 面板完成确认。

推荐流程：

```text
定时/手动触发
  -> GitHub Trending 采集
  -> GitHub API 元数据补全
  -> 候选评分与去重
  -> 人工选择或默认推荐
  -> LLM 生成脚本/标题/标签
  -> TTS 生成音频/字幕时间戳
  -> Revideo 模板渲染
  -> FFmpeg 合成 MP4
  -> 人工审核
  -> 半自动发布
  -> 台账记录与通知
```

## 7. 技术选型

### 7.1 数据采集

默认方案：

- 使用 Playwright 抓取 GitHub Trending 页面。
- 使用 GitHub REST API 或 GraphQL API 补全仓库详情。
- 使用缓存和去重表避免重复生成同一项目。

选择理由：

- Trending 页面是日榜语义的直接来源。
- API 补全比纯 DOM 抓取更稳定，适合读取 README、Topics、Star、语言和更新时间。
- Playwright 只负责榜单入口，降低 DOM 变动对核心数据质量的影响。

关键字段：

- 仓库全名：`owner/name`
- 仓库 URL
- 描述
- 主语言
- Topics
- 总 Star 数
- Fork 数
- 今日热度信号
- README 摘要
- 最近更新时间
- 创建时间
- License

### 7.2 选题评分

MVP 推荐使用规则评分，不引入复杂机器学习模型。

推荐分计算方向：

```text
推荐分 =
  日榜热度分
  + 总 Star 背书分
  + README 可解释性分
  + AI/开发工具相关性分
  + 项目新鲜度分
  - 重复题材惩罚
  - 异常项目惩罚
```

过滤规则：

- 排除 README 过短或无法解释核心用途的项目。
- 排除描述为空、链接异常、明显无关或低质量仓库。
- 排除近期已生成过视频的仓库。
- 对创建时间极短但 Star 异常飙升的项目增加人工确认提示。
- 对非中文受众难以理解的纯内部库或极窄领域项目降低优先级。

### 7.3 内容生成

默认方案：

- 使用 DeepSeek V4 Flash 生成项目摘要、标题候选和标签。
- 使用 DeepSeek V4 Pro 或同级强推理模型生成最终脚本。
- 通过 Model Adapter 抽象模型供应商，保留 OpenAI、Claude、Gemini 或本地模型替换空间。

脚本输出必须为结构化 JSON，不允许只返回自然语言段落。

脚本结构：

```json
{
  "title": "视频标题",
  "coverText": "封面文案",
  "description": "发布简介",
  "hashtags": ["GitHub", "开源项目", "AI工具"],
  "segments": [
    {
      "type": "hook",
      "durationSec": 5,
      "voiceText": "配音文本",
      "screenText": "屏幕主字幕",
      "visualHint": "视觉提示",
      "emotion": "excited"
    }
  ],
  "cta": "结尾引导"
}
```

脚本要求：

- 前 3 秒直接给出悬念、痛点或强利益点。
- 避免“大家好，今天介绍”这类低效开场。
- 用普通开发者能理解的话解释项目价值。
- 明确说明项目解决什么问题、为什么火、适合谁用。
- 必须包含 GitHub 项目名、核心能力、技术亮点和使用场景。
- 不夸大项目能力，不编造未在 README 或元数据中出现的事实。
- 结尾包含收藏、评论区获取链接或关注后续推荐的 CTA。

### 7.4 TTS 与字幕

默认方案：

- 使用 Fish Audio 或具备同等能力的 TTS 服务。
- TTS Adapter 必须支持返回音频文件和字幕时间戳。
- 时间戳优先使用词级或短句级，最低要求为句级。

输入要求：

- 支持情绪提示，例如兴奋、停顿、强调、疑问等。
- 支持中文自然口播。
- 支持稳定批量调用。

输出要求：

- 音频格式：WAV 或 MP3。
- 字幕格式：JSON，必要时同时导出 SRT。
- 每个字幕单元包含文本、开始时间、结束时间。

### 7.5 视频渲染

默认方案：

- 使用 Revideo 作为程序化视频模板引擎。
- 使用 FFmpeg 进行音视频合成与编码。
- 首版采用代码 PPT 风，不引入数字人。

成片规格：

- 比例：9:16
- 分辨率：1080x1920
- 帧率：30fps
- 时长：60-90 秒
- 编码：H.264
- 容器：MP4
- 音频：AAC

画面结构：

- 开场 Hook：大标题、热度数字、项目名。
- 项目卡片：仓库名、Star、语言、简介。
- 核心卖点：2-3 个功能点。
- 代码或截图展示：README、终端效果、项目 UI 或代码片段。
- 动态字幕：跟随 TTS 时间戳逐句或逐词高亮。
- 结尾 CTA：收藏、关注、评论区链接提示。

模板要求：

- 字体清晰，移动端可读。
- 单屏文字不超过 3 行主信息。
- 高亮色用于项目名、Star 增长和关键能力。
- 不使用过度花哨转场，保持科技类内容可信度。
- 模板参数化，不能为单个项目硬编码画面。

### 7.6 编排与任务状态

默认方案：

- n8n 作为流程控制面。
- 渲染任务采用异步模式，避免长时间阻塞工作流。
- 微服务通过 HTTP API 接收任务并返回任务 ID。
- 渲染完成后通过 Webhook 回调 n8n，或由 n8n 轮询任务状态。

任务状态：

- `created`：任务已创建
- `collected`：采集完成
- `scored`：评分完成
- `script_generated`：脚本生成完成
- `tts_generated`：音频和字幕生成完成
- `rendering`：渲染中
- `rendered`：成片生成完成
- `review_pending`：等待人工审核
- `approved`：审核通过
- `rejected`：审核拒绝
- `published_manual`：人工或半自动发布完成
- `failed`：任务失败

### 7.7 发布

国内平台首版采用人工确认和半自动发布。

系统需要输出发布素材包：

- MP4 成片
- 封面图
- 标题
- 简介
- 标签
- GitHub 项目链接
- 推荐发布时间
- 平台适配备注

首批平台：

- 抖音
- 视频号
- B站
- 小红书

首版不实现自动绕过登录、验证码、风控或平台审核的脚本。

## 9. API 设计

### 9.1 采集候选项目

```http
POST /api/jobs/collect-github-daily
```

请求：

```json
{
  "language": "all",
  "since": "daily",
  "limit": 20
}
```

响应：

```json
{
  "jobId": "collect_001",
  "candidates": []
}
```

### 9.2 生成脚本

```http
POST /api/jobs/generate-script
```

请求：

```json
{
  "repoFullName": "owner/name",
  "style": "code_ppt",
  "durationSec": 75,
  "audience": "chinese_developers"
}
```

响应：

```json
{
  "jobId": "script_001",
  "script": {}
}
```

### 9.3 生成音频

```http
POST /api/jobs/generate-tts
```

请求：

```json
{
  "taskId": "task_001",
  "voice": "default_cn_tech",
  "script": {}
}
```

响应：

```json
{
  "audioUrl": "https://storage.example/audio.mp3",
  "subtitleUrl": "https://storage.example/subtitles.json"
}
```

### 9.4 渲染视频

```http
POST /api/jobs/render-video
```

请求：

```json
{
  "taskId": "task_001",
  "template": "github_daily_code_ppt_v1",
  "scriptUrl": "https://storage.example/script.json",
  "audioUrl": "https://storage.example/audio.mp3",
  "subtitleUrl": "https://storage.example/subtitles.json"
}
```

响应：

```json
{
  "renderJobId": "render_001",
  "status": "rendering"
}
```

### 9.5 审核回调

```http
POST /api/review/decision
```

请求：

```json
{
  "taskId": "task_001",
  "decision": "approved",
  "comment": "可以发布"
}
```

响应：

```json
{
  "status": "approved"
}
```

## 10. 审核与质量控制

### 10.1 自动检查

系统在进入人工审核前必须完成以下检查：

- 视频文件存在且可播放。
- 音频时长与视频时长差异不超过 1 秒。
- 字幕文件存在且时间戳递增。
- 标题不为空。
- 简介不为空。
- GitHub 链接有效。
- 脚本中没有明显占位符或 JSON 解析失败残留。
- 不包含明显虚构事实，例如不存在的性能指标、融资信息或官方背书。

### 10.2 人工审核项

审核人员需要确认：

- 项目确实存在且链接正确。
- 视频没有严重事实错误。
- 标题没有过度夸大。
- 封面文字清晰。
- 字幕没有明显错别字。
- 配音自然且没有大段断裂。
- 平台发布文案适合目标平台。

### 10.3 拒绝与重试

如果审核拒绝，需要支持以下操作：

- 重新生成标题和简介。
- 重新生成脚本。
- 重新生成配音。
- 重新渲染视频。
- 放弃该项目并选择下一个候选项目。

## 11. 异常处理

### 11.1 GitHub 采集失败

- 首次失败后等待 1-3 分钟重试。
- 重试仍失败时，切换到 GitHub Search API 备选逻辑。
- 如果仍失败，通知运营人员并结束当天任务。

### 11.2 LLM 输出异常

- JSON 解析失败时，使用修复提示词请求模型重新输出。
- 事实字段缺失时，不允许模型自行编造，必须回退到项目元数据。
- 连续失败 3 次后，标记任务失败并通知人工。

### 11.3 TTS 失败

- TTS 调用失败时重试。
- 如果时间戳缺失，允许降级为句级字幕。
- 如果音频生成失败，任务不得进入渲染阶段。

### 11.4 渲染失败

- 记录 FFmpeg 和 Revideo 错误日志。
- 支持相同素材重新渲染。
- 连续失败后通知人工，不自动发布。

### 11.5 发布风险

- 首版不执行无人值守发布。
- 人工发布完成后再补充平台链接。
- 不保存明文平台账号密码。

## 12. 安全、合规与版权

- 不绕过平台登录、验证码、审核或风控机制。
- 不抓取需要登录或违反服务条款的私有内容。
- GitHub 项目介绍必须基于公开 README、仓库元数据和官方链接。
- 视频中使用的字体、背景音乐、音效和视觉素材必须具备可商用授权。
- 模型生成内容不得声称项目具备未验证能力。
- 账号发布前保留人工确认，降低误发风险。

## 13. 验收标准

### 13.1 功能验收

- 可以手动触发一次完整任务。
- 可以自动获取 GitHub 日榜候选项目。
- 可以展示至少 3 个候选项目及推荐理由。
- 可以为选中项目生成结构化脚本。
- 可以生成配音和字幕时间戳。
- 可以渲染出 1080x1920 MP4。
- 可以输出标题、简介、标签、封面和视频文件。
- 可以进入人工审核流程。
- 可以记录发布台账。

### 13.2 质量验收

- 成片时长在 60-90 秒之间。
- 前 3 秒具备明确 Hook。
- 视频主字幕在手机屏幕上可读。
- 字幕与语音整体同步。
- 内容没有明显事实错误。
- 视频风格统一，适合科技类账号。

### 13.3 稳定性验收

- 单次任务失败时有明确错误状态。
- 关键阶段支持重试。
- 中间产物可追溯。
- 一天内重复运行不会重复推荐同一项目。

## 15. 默认假设

- 首版以 MVP 闭环为目标，不做完全无人值守量产。
- 首批发布平台以国内平台为主。
- 视频风格采用代码 PPT 风。
- 人工审核是首版必须存在的流程节点。
- 技术供应商均通过 Adapter 抽象，避免锁死在单一 LLM、TTS 或发布网关。
- 当前 PRD 不要求立即实现代码，只定义后续工程实现的产品和技术边界。
